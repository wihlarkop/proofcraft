# Pattern Selection

Problem first, pattern second.

1. Name the concrete problem or force.
2. Check whether the repository already has a suitable pattern.
3. Prefer the simplest design that preserves required invariants and boundaries.
4. Use a named pattern only when it clarifies the solution or reduces meaningful complexity.
5. Record consequences when the choice is durable.

Avoid pattern shopping and architecture-by-vocabulary. Factory, Strategy, Repository, CQRS, Saga, Outbox, Clean Architecture, and similar names are tools, not goals.
